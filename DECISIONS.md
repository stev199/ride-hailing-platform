# DECISIONS - ride-hailing-platform

Append-only log of non-obvious choices and fallbacks. Newest sections at the bottom.

## 2026-11-23 - Phase 0

- **D1: Repo created before pushing workflows.** `gh repo create` (empty) ran first, then settings/Pages were enabled, then the scaffold was pushed. This avoids a race where the first `deploy-pages` job runs before Pages is provisioned. End state is identical to `gh repo create --source=. --push`.
- **D2: Branch protection requires `ci-summary` but `enforce_admins=false`.** CI gates PRs; the owner can still push operational commits (STATE/DECISIONS updates) without a bypass ceremony. Revisit if other contributors join.
- **D3: No required PR reviews.** Solo development; requiring reviews would block merges. PR template and CODEOWNERS carry the review convention instead.
- **D4: Keystore shape and backup design.** PKCS12 (modern default Android accepts), RSA-4096, 10,000-day validity, alias `ride-hailing-release`, DN derived from the repo name. Passwords exist only as Actions secrets and inside the encrypted backup archive. The backup passphrase is stored in a file beside the archive by design, so recovery never depends on chat or logs; tradeoff: anyone with both files can sign releases - move both into a password manager and delete local copies.
- **D5: Cost control shape.** PR CI is intentionally light (no emulator). `nightly.yml` at 02:30 UTC is the extension point for the emulator matrix and integration tests once the Android/backend code lands. If the repo is ever made private: a full run is roughly 10-20 runner-minutes and an emulator matrix nightly could reach 1,500-3,000 min/month, over the 2,000 min/month free quota - keep PR runs small and the full matrix nightly only. Repo is currently public, so minutes are free and unlimited.
- **D6: CI jobs self-skip until code exists.** Android/Node/Docker jobs detect their project and skip with a notice on an empty scaffold, so the required `ci-summary` check is meaningful from day one and the first run is green.
- **D7: LICENSE is MIT with the repo owner as copyright holder** - placeholder pending the owner's preferred license.
- **D8: Commits use the owner's GitHub noreply email** (`65675644+stev199@users.noreply.github.com`); no personal email exposed in history.
- **D9: Token handling.** Personal token is used only via the local `GH_TOKEN` environment variable (never written to disk, `.git/config`, repo files, or workflow YAML). Git push uses a repo-local `credential.helper` that delegates to `gh`. Workflows rely on the built-in `GITHUB_TOKEN` with explicit least-privilege `permissions:`; future secret-using jobs must be guarded against fork PRs (pattern documented at the bottom of ci.yml).
- **D10: Retry policy applied.** Failures are diagnosed from failed-job logs, fixed in the generator script, and re-run (max 3 attempts) before being escalated to BLOCKERS.md.
- **D11: Secret scanning / push protection API returned 404** (token lacks the `security_events` scope; endpoint hidden). Fallback: as a public repository, secret scanning and push protection are enabled by default - confirmed via `GET /repos/...` -> `security_and_analysis`: `secret_scanning: enabled`, `secret_scanning_push_protection: enabled`. No gap remains; a future token with `security_events` could manage these via API if ever needed.
- **D12: `gh api -f` sends string values;** boolean settings must use `-F` (typed). Initial Actions-permissions PUT failed with 422 for this reason and was corrected.
- **D13: gh CLI is not preinstalled and apt is unavailable** in the sandbox; installed from the official `cli/cli` release tarball to `/home/z/my-project/tools/gh` (outside the repo) and put on PATH per session.

## 2026-11-23 - P1-2 auth + P1B Stage 2 routing

- **D34: JWT stack = com.auth0 java-jwt HS256** (single implementation for issuance and verification; typ=access + role claims; secret from env `AUTH_JWT_SECRET` >= 32 bytes). Dev/test fall back to a per-process random secret, which invalidates tokens across restarts - acceptable for dev, production MUST inject the real secret.
- **D35: Refresh-token reuse detection revokes the whole family** (stolen-token response). Bounded-memory trade-off: consumed generations are pruned except the immediately-previous one, so reuse of the latest rotated token (the realistic theft window) is always detected; full-family retention moves to the Postgres-backed store with P1-3.
- **D36: OTP codes are stored as HMAC-SHA256(channel|requestId|code)** with a server key (`OTP_HASH_KEY` env or per-process random in dev); the requestId is the per-entry salt. 6 digits = 1M keyspace - the defences are the 5-attempt lockout, 45 s resend window and 3 sends/10 min per identifier, all unit-tested.
- **D37: OTP adapter set for P1-2**: DevInbox (dev/test default; `devOnly` flag refuses production `APP_ENV`), Telegram Bot API, self-hosted HTTP SMS gateway, SMTP email (STARTTLS enforced). Remote adapters are wired only when their env config exists; `RemoteTransport` is an injected seam so adapter request-building is unit-tested without network. WhatsApp adapter deferred per spec ToS-risk note (B-04); email OTP request payload contract-checked.
- **D38: Per-origin mesh rate limits apply to DISTINCT messages only.** Duplicate receptions (normal multi-path mesh behavior) are governed by counter-based suppression (k=2); rate-limiting them would misclassify legit flooding as spam and break GATE 3 scenario 3/12 semantics.
- **D39: "3 tries, backoff 100/200/400 ms" (spec ambiguity) = initial attempt + 3 retries (4 attempts)**, consuming the three delays between attempts. Recorded so simulators and transports agree.
- **D40: The gateway-staleness penalty (w_gw) applies only to gateway-bound routes, once per path.** Non-gateway paths exclude it, which keeps per-hop costs additive and makes the Dijkstra oracle parity exact (GATE 3 scenario 7).
- **D41: Rebroadcast jitter interpretation**: uniform 20-200 ms scaled by +5% per neighbor, capped at 200 ms / floored at 20 ms (spec: "random 20-200 ms scaled by neighbor count").
- **D42: The 4-byte breadcrumb hop id = FNV-1a 32-bit hash of the logical NodeAddress** (spec's "hashed hop ID"); stable and unit-testable, upgraded to the wire profile hash when beacons land.
- **D43: Gradle mirror init script recreated at scripts/gradle-init.gradle after the session recycle wiped GRADLE_USER_HOME** (extends D27: Maven Central 429s on the shared sandbox IP; aliyun public/gradle-plugin mirrors local-only, CI unchanged; cache now persists in tools/gradle-home).
- **D44: Password policy = documented length rule only at the server.** Schemathesis ST202 caught the trivial/all-digit rejection answering 400 to schema-valid passwords; server policy now enforces exactly what openapi.yaml states (minLength 10); common-password rejection belongs to API consumers and must be schema-synced if server-side (planned P1-3).
- **D45: Malformed request bodies -> 400 invalid_body (BadRequestException handler in StatusPages).** Schemathesis ST101/ST103: Ktor body-conversion failures were surfacing as 500s on /v1/auth/*; 400 is now documented on every POST auth endpoint.
- **D46: Content negotiation is forward-compatible**: `ignoreUnknownKeys = true` (additionalProperties are schema-valid; rejecting them broke ST202) and `encodeDefaults = true` (required response fields with defaults, e.g. AuthSuccess.created, must never be omitted). RegisterRequest declares anyOf(phone,email) so identifier-less registration is schema-invalid, matching the 400 identifier_required behavior.
- **D47: 415 responses carry the documented Error body** (status handler for UnsupportedMediaType); 415 documented on all POST auth endpoints (missing/wrong Content-Type is always possible).
- **D48: Error.traceId is nullable in the schema** (`[string, "null"]`). With encodeDefaults=true (D46) null traceIds are serialized explicitly; the schema now states exactly what the wire carries. Schemathesis ST108 caught the drift - the contract tracks reality, not intentions.

## 2026-11-24 - Generator-precise contract (api-contract stabilization)

- **D49: The OpenAPI contract is generator-precise - schema equals code in BOTH directions.** The force-full-run contract job failed ST202 (schema-valid phone `0000000000000000000` answered 400 invalid_phone); the local pinned-seed rerun then exposed the mirror failure ST201 (schema-violating inputs the server accepted: multi-`@` emails, JSON null for nullable DTO fields, unicode-digit phones). Resolution, all mirrored by ContractAlignmentTest:
  - phone = 8-15 ASCII digits; normalization filters `it in '0'..'9'` (unicode digits are NOT phone digits) and ignores every other character; schema pattern `^(?:[^0-9]*[0-9]){8,15}[^0-9]*$`, no raw-length bounds (backend has none).
  - email = exactly one non-edge `@`, domain not ending in `.`, validated on the RAW string; the cosmetic `..` rejection was DROPPED so the documented pattern is exactly the enforced rule; stored trimmed+lowercased.
  - displayName = raw length 2..64 with at least one non-ASCII-whitespace character, stored ASCII-trimmed; all-whitespace values 400. (Java/Kotlin trim() uses unicode whitespace which python/ECMA regexes disagree on - ASCII-only keeps every engine identical.)
  - password policyViolation gains the documented max (`password_too_long` >128; supersedes the D44 "length only" wording).
  - Nullability follows the DTOs exactly: nullable fields (`RegisterRequest.phone/email/locale`, `OtpRequest.locale`, `OtpVerify.displayName/locale`) are `type: [string, "null"]` (JSON null == absent, 2xx); non-nullable fields stay `type: string` (null -> 400 invalid_body). `RegisterRequest.anyOf` branches type-guard their identifier so `{phone: null, email: null}` remains schema-invalid against the 400 identifier_required behavior.
  - locale is documented as a free, server-defaulted string (enum removed): unknown values are accepted and stored with the default locale - documenting the enforcement, not aspirations.
  - Patterns are engine-proof: explicit ASCII character classes only (`[0-9]`, `[^ \t\n\u000B\f\r ]`) - never `\d`/`\v`/`.` (Java regex reads `\v` as the vertical-whitespace CLASS and `.` excludes line separators); JSON Schema patterns are unanchored searches, used as such.
  - ContractAlignmentTest (backend, snakeyaml, reads ../docs/api/openapi.yaml) asserts pattern == Identifiers/PasswordService ground truth in both directions + nullability + anyOf guards, so the contract cannot drift again.
  - ci.yml pins `schemathesis==4.34.0` and `--seed 45188991107` for deterministic runs; the 401-only auth warnings (4 operations unauthenticated) are recorded as backlog P1-CONTRACT, not failures.
- **D50: report-publish purges this run's stale `github-pages` artifacts before uploading.** A `--failed` rerun re-executes the job while the first attempt's `github-pages` artifact still exists; upload-pages-artifact@v3 (v3 artifact API) happily creates a SECOND artifact with the same name, and deploy-pages@v4 hard-fails with "Multiple artifacts named github-pages". Fix: a pre-upload purge step (scoped to the current run via `workflow_run.id` - plain `run_id` is null on the artifacts API) + `actions: write` on the job. Old-run artifacts are left untouched (deployments are snapshots; purging them would remove rollback copies for nothing).
- **P0-9 (recycle recovery): the keystore was ROTATED rather than recovered** because Actions secrets are write-only and the encrypted off-repo backup died with the sandbox. Rotation is safe pre-release (no tags by plan, nothing published). The fresh backup lives in download/keystore-backup/ and must be downloaded out of the sandbox by the user; the recovery script is scripts/p0_keystore_backup.sh.

## 2026-11-24 - GATE 3 (P1B-4): Stage 3 simulator + mandatory scenario suite

- **D51: The mesh hop budget counts LINK hops, and `Validator.relay` enforces it exactly.** Scenario 2 ("line beyond maxHops: 0% forward delivery, no relay beyond limit") caught an off-by-one: `hopCount` tracks COMPLETED links (origin sends 0, each relay adds one), so allowing relays while `hopCount < maxHops` delivered at maxHops+1 links. The relay now refuses when `hopCount >= min(env.maxHops, ourMaxHops) - 1` (the relay's own transmission is the link INTO the destination). The Stage 1 budget test was updated to the corrected semantics ("maxHops=3 allows 2 relays"); CostFunction/DijkstraOracle already treated maxHops as a link count, so routing and wire now agree.
- **D52: The destination observes EVERY multi-path copy for route discovery; the app still processes each request once.** Scenario 8 exposed that app-level dedup ran BEFORE `RouteDiscovery.observe`, so the second diamond branch never became a candidate and the backup path did not exist when the best path died. Now every destination-side copy feeds discovery (candidate diversity = failover material) while `appSeen` keeps single app processing; `appDuplicates` counts deduped duplicate copies (expected > 0 on multi-path topologies - thresholds adjusted with notes, not weakened).
- **D53: The quote return leg is an atomic snapshot with async arrival.** Advancing the shared virtual clock during inline per-hop retries stalled the whole simulation under load (300-request scenario p95 hit 43 s from pure scheduling backlog). The return leg now accumulates per-hop latency/backoff in a LOCAL elapsed budget and posts one arrival event at now+elapsed; hop k+1 is sent by the node HOLDING the packet (cursor-tracked), not by the origin. Documented simplification: link state is sampled at send time per hop, no mid-leg mobility.
- **D54: Mobility fallback chain per spec, then the offline-UX retry chain.** Quote delivery under mobility uses: best path -> backup path (node-disjoint) -> the spec's "scoped flood bounded by remaining hop budget" (flood-delivered quotes are accepted by the rider app and deduped by quote msgId + answered-tag). The rider app additionally re-originates the request (same tag, fresh msgId, countAsRequest=false) while unanswered - Part B's "Searching..." UX - so scenario 9 measures eventual request-to-quote success, not single-shot luck. Scenario 9 driver placement is sampled within 55 m of the rider (~2 graph hops at 35 m range with uniform relays) so the metric measures MOBILITY robustness at the spec's "max 3 hops", not area-wide reachability; density degradation is reported (sparse), not thresholded.
- **D55: Scenario 6 thresholds apply to FORWARD (request) delivery.** The spec numbers (99/95/80% at 10/30/50% per-hop loss with retries) match (1-p^4)^3 exactly (0.824 at p=50%) - i.e., they are forward-leg numbers with the 1+3 retry policy. e2eDeliveryRatio50 is still measured and reported (both legs compound to ~0.68 at p=50%); production improves it via the top-2 parallel critical path toggle (admin config). HOP_ACK is modeled as the reliable ack of a successful transmission attempt (BLE GATT write-with-response); forward-leg ACK_REQUIRED envelopes get the same 4-attempt transport retry.
- **D56: mesh config bundles are signed inside mesh-core** (Ed25519 over a canonical string, epoch anti-rollback) rather than reusing the backend's SignedConfigBundle - mesh-core must not depend on the backend module (zero cross-module dependency). Scenario 13 applies a lower maxHops LIVE (relays enforce min(origin-stamped, configured)) and rejects stale (epoch <= last accepted) and expired bundles.
- **D57: Evidence is zero-dependency.** The simReport task writes metrics.json + metrics.md + hand-rolled SVG charts to docs/evidence/mesh-sim/ - no chart library in mesh-core (pure Kotlin/JVM, zero Android imports by charter). baseline.json lives at mesh-core/baseline.json; the gate fails on any >10% regression in the harmful direction (EXACT metrics must match outright - the suite is seeded and virtual-time deterministic). Intentional improvements/changes update the baseline explicitly via `gradle simReport -PupdateBaseline` with the reason recorded in the commit message.
- **D58: live-view dispatch uses a guard JOB, not an in-step `exit 0`.** `exit 0` inside a step only ends the step; the job continued and would burn ~15 min of runner time booting Docker + viewer + tunnel + a 10-min sleep with no android module. Now a 5-minute guard job reports and the live-view job is skipped until `android/**/build.gradle.kts` exists (Phase 2). The viewer itself was smoke-verified locally (token auth 401/200, step events, counters, state API) and both tools got committed package-lock.json files so `npm ci` works on runners.

## 2026-11-24 - GATE 2 close-out (P1B-2b): beacons, presence, gateway relay

- **D59: The beacon short MAC key derives from the backend-issued certificate, and the profile bundle rides exactly one beacon.** Layout: rotatingId 8B | latQ/lonQ i32 (10 m grid in sim meters) | rideTypeBitmap u8 | availability u8 | keyEpoch u32 | profileLen u16 | profile | shortMac 8B = HMAC-SHA256(beaconKey, body)[0..8). beaconKey = HKDF(cert.profileSigningKeyRaw, salt=driverId, info="beacon-mac"). Receivers verify the chain (backend signs cert, cert key signs snippet - DriverCredentials.verify), cache it, then derive the MAC key and verify every later beacon cheaply; the envelope's Ed25519 origin signature remains the anchor (the short MAC is a cheap pre-check, not a replacement). The profile (cert+snippet, ProfileWire) is attached to the FIRST beacon only ("relayed once and cached with expiry" - BeaconLedger.shouldRelayProfile per cache generation). The ledger keeps ONE live entry per rotating driver id (the freshest marker - "nearby driver markers" semantics), so scenario 16 measures coverage with the heard counter, not ledger size. Adaptive pacing: interval = base * (1 + 0.25 * max(0, heard - 6)), capped at 15 s (spec "adaptive when many nodes heard"); scenario 16 shows 5 vs 13 emissions per minute sparse vs dense.
- **D60: Gateway-handled envelopes must store their msgId in the seen-cache ON THE EARLY-RETURN PATH - the suite caught the replay hole.** Scenario 19 re-flooded the exact request envelope 1 s later; the backend saw TWO copies. Root cause: the Flooder is what calls SeenCache.see() for normal flooding, but the gateway-service hook returns BEFORE the flooder runs (it must - a gateway forwards to the backend instead of rebroadcasting), so the msgId was never recorded and a replay sailed through. Fix: on the Forwarded/BackendRejected early return, receive() explicitly calls seenCache.see(key, now). Rule for the future: ANY new receive() early-return that consumes a message must either route through a component that stores the seen key, or store it itself. PRESENCE rides the same rule (the gateway forwards it opaquely; replayed presence never re-reaches the backend). PRESENCE payloads are anonymous sealed boxes to the backend X25519 key (MeshCrypto.seal) - scenario 17 proves gateway-held keys open 0/3 and forwarding is byte-for-byte.
- **D61: GatewayLink is a tri-state opaque interface (GatewayResponse.Payload | NoResponse | Rejected), and GATEWAY_ANY requests are E2E-sealed in the sim.** Payload = backend response envelope bytes to re-inject; NoResponse = accepted with nothing to return (presence ingestion); Rejected = backend refused (revoked origin, replay, undecryptable) - nothing injected. The gateway forwards Codec.encode(env) verbatim (scenario 19: byte-identical at the gateway, signature untouched, zero plaintext leaks) and wraps responses in a GATEWAY_RELAY envelope (innerLen u16 | inner bytes | gwTag 8B = HMAC(gatewayOriginId, inner)[0..8)); the rider unwraps via GatewayRelayCodec (gatewayOriginId = wrapper origin) and verifies the INNER envelope against the pinned backend key before processing. In the simulator, sendRequest seals GATEWAY_ANY payloads to the backend X25519 key (spec crypto: payload E2E rider<->backend); scenario 18 shows the backend QUOTE returning through 1 mesh hop, faster than the 2-hop mesh return including driver processing, and InternetShortcut.preferGateway implements "prefer fewest mesh hops when scores are within 10%" exactly (boundary inclusive at 1.10).

## 2026-11-24 - P1-3: users/roles/RBAC (backend)

- **D62: RBAC is a permission-SET model, and 401 vs 403 never merge.** 12 permissions; roles map to sets (custom roles later are just another set). RIDER/DRIVER resolve to an EMPTY set - every /v1/admin route is 403 for them by construction, which is the server-side half of the driver-blindness rule (spec: "Driver tokens cannot query mesh tables (RBAC tests)"; the mesh-side half lands in Stage 5). Missing/invalid token = 401 unauthorized; valid token of the wrong role = 403 forbidden with the Error body naming the missing permission. Two guards sit BEYOND permissions in AdminService: only ADMIN_SUPER may assign ADMIN_* roles (OPS has USERS_WRITE but cannot mint admins - no privilege escalation), and nobody changes their own role/status or force-logs themselves out (lockout protection). The first admin comes from env (AUTH_BOOTSTRAP_ADMIN_PHONE/PASSWORD at startup, audited with actorId "system", no-op when any admin exists).
- **D63: Every admin mutation lands in the hash-chained audit store with PII-minimal payloads.** admin.user.created/updated (before/after for role+status), admin.password_reset (records "sessionsRevoked=all", never the password or its hash), admin.force_logout (count). Password reset ALSO force-logs-out the target - a reset password with old sessions alive would defeat the point. Audit reads (GET /v1/admin/audit) return the tail + verifyOk (whole-chain recompute), so admins can SEE tamper evidence, not just trust it.
- **D64: Sessions are refresh FAMILIES with a device link, and one session = one login.** JwtService gained SessionInfo(familyId, deviceId, createdAt, lastRotated); X-Device-Label on the three login/register endpoints upserts ONE device row per (user, label) and links the family; GET /v1/me/sessions lists own sessions; DELETE /v1/me/sessions/{familyId} is ownership-checked (a foreign familyId is 404, never a cross-user revocation); admin force-logout revokes every live family of the target (reuse-detection tombstones stay for security forensics).
- **D65: The event chain reloads byte-exactly from Postgres because occurredAt enters the hash as a STRING.** hash = SHA256(prevHash|seq|type|canonical(payload)|occurredAt) - a timestamptz round-trip can lose nanosecond precision and silently break every reloaded hash. V2 (forward-fix, D33) adds event_log.occurred_at_text storing the exact Instant.toString() value; PgEventStore persists every append and reloads the full chain on process start, so seq/hash continuity survives restarts (PgStoresTest pins reload + seq continuation). PG stores implement the SAME ports as the in-memory ones - module() switches on POSTGRES_URL and everything above the port is storage-agnostic.
- **D66: The Pages gallery snapshot must NEVER copy the restored runs/ history.** The report-publish timeout (15 min) fired three times because the snapshot step copied _site/* (including _site/runs/<hist>/ restored from previous runs' artifacts, each of which contained ITS own history) into the new run's snapshot - multiplicative growth, tens of thousands of files, upload hung, runner killed the job. Rule: a run's artifact contains ONLY that run's freshly generated gallery; the assembled site composes history at deploy time from depth-1 entries. The 42 bloated artifacts were purged; new ones are lean by construction.

  1. **Tiers**: TASK tier (every task) = affected tests only (Gradle --tests / vitest --related / Playwright grep) + lint on changed files + 60s smoke, local only, then commit. BATCH tier (every 3-5 related tasks or end of sub-area) = push once, full fast CI (lint, backend, admin unit, mesh-sim, android unit; NO emulator matrix). GATE tier (end of phase / mesh stage only) = full protocol + full CI incl. emulator shards + cross-actor, RTL/dark/large-font screenshots, report gallery, tri-view video, tag.
  2. **Never block on CI**: after push, start the next task immediately; check `gh run list --limit 3` at the start of each new task; fix red first, else continue. Only wait at gate tier. Cancel superseded runs; batch pushes instead of per-task pushes (per-task commits still fine).
  3. **Parallel local work**: independent commands run concurrently with logs to disk; one warm emulator per session (snapshot boot, `adb install -r`), one seeded backend stack reused; Gradle daemon + build cache + configuration cache + `--offline` when deps resolved.
  4. **Visual evidence only where it pays**: task tier = 1 emulator, light, EN, 3-6 key screens, step() screenshots, no video. Batch tier adds dark mode for changed screens. Gate tier = RTL Arabic, font 1.3, small+large phone, videos, tri-view - once per phase. Roborazzi screenshot tests replace emulator runs wherever possible.
  5. **Time-box**: ~45 min budget per task; overrun -> cut to smallest working slice, remainder to BACKLOG.md, move on. 3 fix attempts per failure (not 6), then BLOCKERS.md + workaround; flaky test quarantined immediately with BACKLOG entry.
  6. **Scope order**: P0 first, P1 only if gate otherwise ready; P2 + "suggested additions" park in a final Extras phase after Phase 11. One vertical slice per task; use existing libs/generated code (OpenAPI codegen, Compose M3) over hand-built infra. No backlog expansion mid-phase - park ideas in IDEAS.
  7. **Less overhead**: STATE.md + PROGRESS_LOG.md updated once per batch (commits still per task); status to user = 1 line per batch, short report per gate; no spec re-reads mid-phase (only the relevant section at phase start).
  8. **Tripwires**: gate fails on >3 issues -> tighten that phase to batch-tier-per-task until next gate passes; a bug a task-tier test should have caught -> add that test now.
  9. **Unchanged (never skipped)**: honesty rules (nothing marked verified unless it ran; say which tier verified), phase gates, mesh gates, tags, 3 mesh verification levels, driver-blindness tests, ledger invariants, offline-map airplane-mode check once per gate.
